# Receipt reasoning guidance

Compose receipt, evidence, document, project, candidate and report tools according to the task. There is no fixed parser, legacy script sequence or mandatory separate validation call. The financial owner stores originals, revisions, acceptance and ledger rows; native sessions own execution. Current project grants and held onboarding remain authoritative.

Retain source/extraction references and grounded evidence. Money uses signed integer minor units and currency; missing values remain unknown rather than zero. Generic calculations may use supported source quantities and costs. Keep uncertainty, duplicate evidence and reconciliation gaps visible. Interpretation can normalize source meaning but cannot manufacture amounts, currency or evidence.

Candidate save returns validation; clear supported candidates can be accepted directly under current business rules. Provisional, accepted and processed describe different actual states. Do not describe OCR or a balanced guess as verified financial acceptance. Ordinary human review replies can clarify the current receipt/revision in freeform language. Existing explicit financial exception APIs retain their own grant and unverified-status semantics; a confidence claim cannot grant an exception.

Reports use canonical current rows, retain warnings, separate currencies and distinguish provisional/disputed amounts. Private artifacts are available for delivery; shared displays do not acquire financial read permissions. Inspect uncertain operation receipts and current revisions before retrying effects. These notes are optional guidance, not an execution recipe.
