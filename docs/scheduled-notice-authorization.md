# Scheduled notice authorization

Implemented source boundary, November 4, 2026. Scheduling remains disabled and historical jobs remain retained and disabled. Provider and owner delivery acceptance is still open.

The native scheduler owns jobs, execution, announcements and its durable outbound queue. The household adapter uses an opaque delivery-only native session key derived from each existing declaration key. The native job owner keeps the originating conversation session unchanged. No second queue, identity store, scheduler or message ledger is introduced. Native job listing is filtered by the existing owner after native pagination because delivery sessions differ from conversation sessions.

Before a new scheduled notice is prepared, the supported native `message_sending` hook recognizes only this reserved delivery session, obtains the exact native job and reloads protected household policy. The existing admission owner checks profile availability, job ownership, current schedule/scope grants, audience and destination. Both the requested destination and any operational notification destination must still be authorized. The guard does not inspect message text. Ordinary live conversation replies bypass this scheduled-only hook.

The queue policy `finish_accepted` defines native acceptance of the prepared immutable message as the external-effect boundary. Current authorization applies to each new preparation. Once the native durable queue accepts that prepared batch, its exact frozen message may finish after a later grant change. Such revocation prevents new preparations; it cannot retract an already accepted message. This also applies to native failure, recovery and auto-disable notices. Cancellation does not undo accepted notices or previous effects.

The installed OpenClaw 2026.9.8 reuses a saved `preparedBatch` on retries and does not rerun `message_sending` for that saved batch. No supported per-provider-attempt policy callback supplies the required job identity. Therefore `recheck_each_attempt` is available as an explicit configuration choice but prevents schedule activation with `native_scheduled_delivery_retry_guard_unavailable`. It must not silently behave like `finish_accepted`. Native global session scope also blocks activation: native operational notices can collapse onto a global session and lose the required per-job provenance.

The preparation guard reuses the existing protected configuration loader and native scheduler lookup. It does not fetch provider URLs, accept model-authored recipients or create message-content routing heuristics. Route failures and policy lookup failures suppress preparation. Unknown sends remain unknown and must be reconciled through existing native delivery state rather than blindly replayed.

A provider-free installed-SDK contract test uses a scoped fake channel registry and the actual native hook runner/preparation implementation. It verifies that current authorization permits preparation and route revocation produces a suppressed entry before any provider send. It does not claim actual provider delivery or retry cancellation. Broader native workflow acceptance and any schedule activation remain separate work.
