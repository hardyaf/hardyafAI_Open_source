# Household task-flow integration

Implementation status: the original Slice 3 baseline established 0.5; the 0.6 simplifications described here are now promoted to the ordinary runtime. Complete household workflow acceptance remains open. This is an application layer over stock OpenClaw. [Current status](current-status.md) owns deployment and current model evidence; the [simplification record](bookkeeping-simplification-implementation.md) describes the smaller implemented model interface without another runtime.

## Reuse and data ownership

| Datum or operation | Decision and authority | Projection / recovery |
| --- | --- | --- |
| Goal, objective, execution status, native parent/child run and yield wake | Reuse native OpenClaw | Handoff stores the original exact binding; refresh native state on every call |
| Human source, mode, identity, device, audience and grants | Reuse household admission and native execution lineage | Root binds trusted context, including descendants; tool arguments cannot supply it |
| Current phase, question, context selection, draft revisions and bound outcome requirements | Adapt existing conversation_checkpoints CAS | One pointer per native session/goal; immutable artifacts retain correction reasons, internal requirement pins and evidence references; failed CAS leaves an unreachable immutable artifact only |
| Handoff, question, analysis/chart/report output | Reuse scoped ArtifactStore | Exact owner/conversation/task/audience; prior handoff pointers retain provenance; no transcript mirror |
| Mutating domain effects and operation evidence | Reuse owning domain effect receipts | Revalidate actual state/digest before task finish and native goal completion |
| Skills and exact tools | Reuse source skills and native Tool Search | household-domains.json maps instructions only; authorized catalog remains the capability authority |
| Clarification waiting | Adapt existing submission projection | Persist question first; settle native run; release reservation and show waiting_for_user. New freeform source enters once through ordinary chat.send in the same session |

No schema migration or new queue/store is needed by this module. Root composition supplies adapters for existing checkpoints, artifact store, live catalog and source evidence.

## Root integration contract

`TaskFlowService` receives `TaskFlowPorts`. Each invocation receives `TaskFlowContext` from current trusted admission plus exact native observations. `native.sessionId/goalId` identify the original goal's canonical checkpoint binding even for a proven descendant; `native.runId` identifies the current permitted execution. Root must recheck lineage, operator control, identity, device, conversation audience and grants through `assertCurrent` before each effect. The raw prompt must match its SHA256 and exact admitted source id.

Dispatch descriptors from `taskToolDescriptors` through the service directly. Task metadata writes have their own existing checkpoint CAS; do not create a second effect/task table for these pointer mutations. Expose native names `household_task_*`. Validate native input schemas before dispatch as for the existing tools.

Ordinary clarification and reply binding use the existing conversation/session null-goal checkpoint without creating a goal. The application supplies their current CAS revision and unique question target when omitted. Explicit multi-phase handoffs and goal completion still require their owning native goal. Matching authorized skill context loads mechanically on first tool use; manual selection is optional preload and cannot expand grants. Ordinary authorized effects, queries and grounded memory curation remain goal-free and source-bound. Explicit stop remains a current-goal control operation.

`buildTaskPrompt` is the typed before_prompt_build helper. It restores only selected domain instructions and compact task data. Native embedded Tool Search remains supported. Domain selection also returns exact scoped tool schemas; coordination schemas are included in the compact prompt. Do not narrow normal toolsAllow to the selected domain list, because the model must select and compose another authorized domain within the same turn. In diagnosis, use the fixed safe allowlist and also the trusted global pre-tool policy.

`finalizeTask` is the typed before_agent_finalize helper. Waiting questions intentionally end the run while the goal remains active. Other incomplete handoffs request a bounded revision; the installed embedded harness has a total limit of three such revisions per run. Productive continuation therefore uses native child/yield/settlement turns, with no application productive turn cap. It never creates an application timer, queue or self-message loop.

The trusted pre-tool boundary must reject native `update_goal {status:'complete'}` unless `service.canComplete(currentContext)` returns true. `create_goal` is advertised and permitted only when the existing trusted system admission callback allows it; the current runtime callback covers an explicitly granted scheduled workflow. Human-authored text or brain-dump mode alone cannot create this policy. Permitted system creation preserves the admitted objective: Main may pass `current request`, and the trusted policy supplies the immutable text and any authorized budget. Explicit app `goalStart` remains the separate supported atomic admission path, binding the formal goal before Main runs. Ordinary actions, brain dumps, clarification and typed analysis stay goal-free and require no additional approval ceremony. Goal pause/resume/clear remain operator control. Native pause must not be used for a clarification: goal resume starts an independent turn and would race the actual answer.

`task.stop` is a typed bridge for the model to interpret a fresh human stop request normally. HouseholdTaskApplication accepts only the current parent/native goal and actual human source, then calls injected `stop(binding,{operationId,note?})`. Root's existing control boundary rechecks owner/operator rights, exact source/goal/run/time and idempotency, applies native pause/cancellation and records its control receipt. It returns `{state:'paused'|'cancelled',goalId,operationId,receipt?}`. Because successful control intentionally revokes admission, there is no checkpoint mutation or ordinary post-effect live-source assertion afterward. It never claims completion or reverses earlier effects. Diagnosis can stop its own task; children and scheduled continuations cannot authorize it.

`ports.evidence` is an owner adapter: accept only the exact requested references, inspect actual committed/source state, emit a stable digest, provenance and typed `effect` facts, and reject unknown/uncommitted/uncertain results. Persisted operation outcomes require `requiredEffect` with the exact receipt-producing write tool, intended business state and an optional exact resource id. During `task.complete`, omission can reuse an existing uniquely matched requirement or derive these mechanical fields from one uniquely verified eligible inline operation receipt. It cannot infer from automatic candidates, mixed/ambiguous references or partially rejected proof; checkpoint declarations remain explicit. Existing owner/human acceptance and resource bindings remain protected. Reads return observations and do not issue committed operation IDs; a readback can inform Main without becoming another operation outcome. The optional `operationToolNames` port projects the current scoped catalog's write tools, so the native application rejects impossible read-tool requirements before persisting them. Verification matches owner-issued tool/state/resource facts during attachment, finish and native completion recheck. Operation receipt existence is insufficient when its owning business result is false or provisional. `verifyTaskArtifact` handles exact scoped immutable output artifacts; input/evidence handoff files cannot prove output. Native child completion alone is deliberately not an exposed evidence kind; verify its actual output artifacts or domain effects instead.

The immutable admitted human/native objective is the task intent. Model-authored outcome drafts and resource hints are internal plans. Main may correct an unverified draft or explicitly retire its ID with `planRevisionReason` in `task.checkpoint` or `task.complete`; the existing immutable handoff history records the reason and current source. Omitting an outcome does not retire it. These changes neither rewrite the original request nor remove committed domain effects.

Once actual owner proof or fresh human steering binds a requirement, internal `requirementAuthority` keeps it protected even if a later strategy change clears its current proof. A uniquely established owner target is retained separately as `boundResourceId`; model inputs cannot supply either internal field. Display wording may change without clearing proof. Same-authority strategy changes retain the bound evidence kind, business state and target and require fresh proof; material target/acceptance changes or retirement need fresh scoped human steering. Domain grants and approval policies remain independent constraints.

Owner proof may provide bounded `effect.resourceIds` for a batch operation. A singular requirement must match an exact owner-issued ID or a member of that set. Multiple IDs are not concatenated into one target, and a batch set is not guessed into a singular binding. Current owner state must still satisfy every retained requirement before completion.

Provide a typed output artifact/report publication capability for report-only diagnosis and ad hoc analysis. Report artifacts can change while operational state remains read-only. Diagnostic mode cannot be granted or removed by tool arguments or document text. Trusted policy must cover retained/deferred tools and all descendants/continuations, deny raw host/provider/config/credential mutation and prevent worker repair. The prompt allowlist is additional context control, never the sole safety boundary.

## Completion without a formal upfront plan

Main can declare actual user outcomes in `task.complete`, after the work. Outcome IDs and revision mechanics are automatic when omitted. Completion gathers current-goal owning operation/output candidates and attaches proof only when uniquely matched; inline references resolve ambiguity. Independently bound requests remain separate results and must not be included as original-task outcomes. Existing outcomes remain required unless explicitly retired under the draft/steering rules above. Declare the requested results, rather than one outcome for every tool invocation. `outcomes_required`, `evidence_required` and `children_pending` are pending results, never completion.

Unavailable explicit proof returns `evidence_required` with bounded `rejectedEvidence`, a total rejection count and current verified `evidenceCandidates`. A requirement naming a tool that issues no write receipt returns `outcomeIssues` with `task_operation_tool_not_receipted`. Invalid proposals are not persisted; Main can correct the draft using actual owner IDs without repeating delivered effects. Explicit source/binding and requirement mismatches also return rejected reference IDs and typed codes with only currently eligible owner facts. The rejection never grants the reference authority, exposes foreign receipt contents, persists the invalid proposal, drops a semantic outcome or repeats an effect. Missing or ambiguous mechanical requirements return `task_operation_requirement_required`. Independently identifiable current-authority and permission failures, unexpected owner errors, changed saved proof and internal candidate-boundary failures remain hard errors; inaccessible artifacts retain the existing privacy-preserving unavailable response.

`task.context` restores compact owner-issued `evidenceCandidates` without changing a checkpoint. Saved proof is freshly re-read against current business state at completion; receipts from another goal cannot establish this goal's result. Committed effects from an earlier cancelled source in the same goal remain visible. Semantic coverage remains Main's responsibility; an arbitrary receipt does not invent the user's outcomes.

`task.complete` coordinates verified handoff readiness and exact native completion. Response-loss recovery requires the exact existing control receipt and source/session/goal binding. Native completion independently rechecks evidence and pending children. Children cannot complete the parent. Legacy verify/finish calls remain compatibility dispatch only and are omitted from the live advertised catalog; ordinary callers use the completion facade.

Native progress is presentation, never effect authority. Independent side topics omit original-goal progress guidance and cannot update that goal through the task guard. The real `progress_card` tool accepts `{}` and receives a trusted truthful projection; an unplanned goal may retain unfinished progress without a formal outcome checkpoint. Unsupported model success labels are not accepted. The actual native callback still owns unfinished-plan continuation; no RPC can forge it and no application self-prompt queue is introduced. Native `sessions_yield` is direct-only: invoke its visible typed function directly, never ToolSearch or a wrapped `tool_call`; it intentionally has no ToolSearch ID. A parent waiting for a child omits `waitFor`; `waitFor: message` means an external-message wait and is denied by the household boundary. Same-agent child creation uses `completionTarget: parent` so native settlement can wake the original parent.

## Failure and rollback

CAS rejects concurrent or stale writes. Mode/session/goal/audience mismatch rejects stale artifacts. Evidence failures leave the native goal incomplete and visible. Source retries must restore the current checkpoint first rather than blindly replay a stale revision. Immutable artifact orphans after a CAS conflict are harmless existing-store evidence and require no feature-private garbage collector.

Roll back the module/plugin wiring and source skill together. Existing native execution, effect receipts and artifacts remain authoritative; retain their records. No migration reversal or legacy Jarvis reactivation is involved.

## Same-conversation topics and transport delivery (0.7 implementation)

Independent `new_topic` replies may perform authorized work while the original question waits. Existing handoffs retain a bounded stack of immutable question references. A side clarification carries application-bound `independentTopicOf` and `independentSourcePromptId`; its answer restores the prior focus and keeps the side source/attachments recoverable. Explicit question selection can return to a suspended topic. Current human input remains the authority for correction/approval; restored source text cannot impersonate a fresh response. Independent effects and outputs receive their own source/topic binding and cannot establish the original goal's outcomes.

Discord's native `message_received` adapter copies staged original image/PDF bytes into the existing ArtifactStore before native source admission. It retains mapped actor/channel/audience, stable message/run identity, hashes and source submission references. The canonical staged `media` facts grant local-read custody; provider-side `originalMedia` does not. An initial remote-staging wait is completed through the supported `message:preprocessed` event, correlated by exact session/message/sender to its native run. Native source admission waits for its exact existing input receipt across worker registries. Pending staging, external paths, symlinks, changed files and oversized input cannot acquire custody; a later ready hook may finish the same admission. Image-only prompts retain the true empty text and require current owned attachments. No URL launcher or second intake store is introduced.

Native schedule declarations now carry a trusted current-conversation or configured notification destination. Explicit `delivery.mode=none` retains quiet work. Creation/update verifies the saved destination; admission and later capability calls recheck destination and audience grants. Execution and delivery status remain separate native facts, including unknown sends. Historical disabled jobs are untouched.

Protected native plugin approvals adapt into the existing question/source/control-receipt authority. Only allow-once/deny is offered; the installed native Discord reviewer contract must prove the exact private operator route. Signed app decisions retain their existing owner checks. Native 2026.9.8 invokes resolution callbacks without awaiting them, so an exact in-flight run/tool-call barrier waits for durable decision persistence before the bound tool executes. Unavailable routing, stale source, denied decisions and uncommitted resolution never authorize an effect. There is no parallel approval queue.

These are source implementation statements. Contract and live transport acceptance must be recorded in the consolidated implementation campaign; none is established by this documentation update alone.


V1 retains one formal native goal per conversation. Independent ordinary actions and nested questions share the chat with separate source/effect scope, but they are not parallel formal native goals. A pending independent question must be resolved or explicitly steered away before completing that conversation's formal goal; otherwise its goal-bound question references would be stranded. Native goal completion closes only that goal's ordinary waiting source records after verified terminal state and no pending question. It never completes an independent topic merely because the original goal ended.

Source settlement distinguishes turn/question state from business delivery. Independent turns inspect only their own pending questions and source-owned child runs, rather than adopting the waiting root goal. Goal-free clarification chains carry one mechanically derived original-source pointer in existing submission metadata; a resolved chain closes its prior waiting turn records. Real owning receipts remain the proof for delivered household actions. Current source/run/session/control fences and immutable question bindings apply during native-end settlement and maintenance recovery alike.

## Ordinary-source goal promotion compatibility debt

Promotion of an already-running ordinary source into a formal native goal is not an implemented atomic admission operation. A raw model `create_goal` could create native state before the application had a matching source/goal binding; the retained analysis attempt demonstrated that failure, followed by fail-closed authority errors. The prompt and native guard now agree that an ordinary source has no goal-creation policy. No late binding relaxation, mode/channel exception, second task engine or automatic replay was added. A future promotion feature must adapt the existing atomic source/native-goal admission boundary before being advertised.

Ordinary analysis uses `household_analysis_start`, a real accepted child and direct `sessions_yield`, then `household_analysis_result` with exact announced manifests. Rejected helper admission must be inspected or reported; it is not permission for raw `sessions_spawn` or `create_goal`. Unknown effects use existing owner inspection. Initial helper rejection and any native SDK compatibility fixes remain separate from this admission alignment.
